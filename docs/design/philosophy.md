# 设计哲学与不变量

本页定义 Imbrex 的不变量。任何改动都不得破坏；要改必须先新增一条[决策记录](decisions.md)，并在 PR 中单独说明理由与代价。

本页只陈述**长期成立的东西**。当前做到哪一步见[项目状态](../progress/status.md)，阶段安排见[开发计划](../progress/plan.md)。

---

## 1. 网关不拥有 Agent，也不要求任何 Agent

Imbrex 不实现模型循环、不保存决策状态、不解释业务载荷。如果某个应用是一个自带模型循环的 Agent，网关给它提供工具与上下文；如果它不是，网关完全不需要知道 Agent 这个概念。

这条决定了大量边界：没有 prompt 编排、没有工具选择策略、没有对话历史管理、没有重试语义上的"模型重跑"。事件载荷 `data` 由具体应用解释，网关保持透传。驱动 Agent 的能力由插件提供，可以整体移除而不影响网关。

## 2. Everything is a plugin

协议入口、连接器、管理面、前端视图一律是插件。宿主只做装配、依赖注入和生命周期。不存在特权模块。

可检验的形式：删除任一非 required 插件，其余部分照常运行；禁用管理插件，网关退化为无头服务；新增一个插件不需要改动宿主或其他插件。

## 3. 协议即插件，方向不混用

没有任何协议是网关必需的。当前提供的入口（REST、MCP、ACP 客户端）各自是可装卸的插件，缺失时其余部分照常运行。

使用时方向固定，不混用：

- **南向 MCP**：Imbrex 是 Server，调用方是 Client。用于暴露能力与上下文。
- **北向 ACP**：Imbrex 是 Client，Agent 是 Server。用于驱动 Agent。

管理动作不注册成调用方可触达的能力，普通调用方凭据不因接入而获得管理权限。

## 4. 事件是事实，消费是应用的事

事件日志 append-only。身份是 `(source, id)`，首次写入胜出，重复身份不产生第二条业务事件。内部序号是 `bigint`，线上是十进制字符串。

每个消费者持有自己的 `last_seq`，主动拉取，通知只用于唤醒而非投递。网关不替应用保存"处理到哪"，也不保证至少一次或恰好一次。

## 5. 能力是唯一的外部效果入口

一切产生外部效果的动作都走能力调用：JSON Schema 校验、Principal 授权、稳定的 `call_id` 幂等、四态结果 `in_progress / succeeded / failed / unknown`。

`unknown` 永不自动重试，也永不改写成成功。可能已发送就必须保持未知，由人核验后显式处置。

## 6. 视图所有权属于插件

管理控制台是一个 Shell 加若干插件自携视图。Shell 只提供登录、视图注册表、插件 loader 和渲染插槽，**不感知任何具体业务**。

视图以 `mount(el, ctx) => teardown` 交付，框架无关。Shell 中出现 `if (module === 'xxx')` 即为违规。插件禁用、加载失败或未装配时，其页面与导航一并消失。

## 7. 依赖方向单向

```
插件 → @imbrex/ui-contract        允许
插件 → 宿主绑定（PluginApi）        允许
插件 → core / storage（经绑定）     允许
插件 → 另一个插件                  禁止
插件 → 宿主内部实现                禁止
ui-contract → 任何插件             禁止
```

`core/` 不依赖 Cordis、不依赖 HTTP/WS 框架，可独立测试。`storage/` 不向上层泄漏原生 SQL。

## 8. 无消费者不抽象

没有第二个使用者的通用层、配置项、框架、脚本一律不建。"未来可能有用"不是理由。

新增抽象的前提是：已有至少两个真实消费者，或一个已发生的缺陷必须靠它才能修。抽象的成本不是写出来的行数，而是它之后每次改动都要经过的那层。

## 9. 缺失即降级，不阻塞宿主

单点缺失不扩大成整体不可用：前端资产缺失 → `/admin` 404，管理 API 与宿主照常；插件启动失败 → 标记并继续；管理插件晚启动、重启或卸载不影响业务插件；`unknown` 调用不阻塞其他调用。

## 10. 文档与代码同源

`docs/` 是唯一设计依据。改公开接口、字段、状态码或配置项，必须在同一次变更里同步改文档。

状态类陈述（"已实现""待验证""当前"）只允许出现在[项目状态](../progress/status.md)。其他文档用现在时描述系统**是什么**，不描述**做到哪一步**——后者必然腐坏。

---

## 变更流程

1. 提出一条新决策，写进[决策记录](decisions.md)，包含选择、理由、代价、何时重评。
2. 在 PR 描述中单列"违反/修订了哪条不变量"。
3. 同步更新本页与该决策涉及的契约文档。

不变量是防漂移的锚点，不是禁令清单。它们约束的是**为什么**，具体实现方式仍按实际需求选择。
