# 架构决策记录

统一开发基线 0.3 · 2026-10-18。以下为最终文档采用的设计选择；实现和运行保证仍以测试为准。

## 1. 主要设计取舍

| 议题 | 最终选择 | 理由与影响 |
| --- | --- | --- |
| 产品与交付 | Cordis + 事件/能力双通道，M0—M2 尽早跑真实闭环 | 演示插件与第二消费者进入首版，验证轻量网关方向 |
| 插件入口 | 一个由宿主绑定的 Imbrex 客户端，提供 events/capabilities 两组 API | 领域服务分离并绑定主体，不同时维护多组同义插件入口 |
| 数据库 | node:sqlite + DB worker；三张核心表 metadata/events/calls | 采用明确的最小表职责；保留完整 event_json，避免丢失可选事件属性 |
| 同步设置 | WAL + synchronous=FULL | 不采用把 NORMAL 描述成断电持久保证的措辞；FULL 的真实环境效果仍须验证 |
| 事件与读取 | first-write-wins、bigint/string、store_id、短事务 through_seq | 保留共同协议；精确规定满页/空页，不恢复签名游标和复杂 GC |
| store_id 范围 | 读取、发布、调用及调用查询均绑定预期存储 | 防止旧客户端在重建后把旧意图送到新存储，仍只有一个标识 |
| 参数与默认值 | HTTP 契约集中规定，分页默认 50、最大 100 | 选有界原型值，不将示例参数作为性能保证 |
| 回复工具 | 实例化 ID + input_event_ref/text；按实际 caller 权限读输入 | 不接受模型任意填写目标，也不借用连接器更大的读取权限 |
| 调用结果 | 全部已有状态都返回原记录；unknown 不自动重发 | 补全失败/未知状态的同键重试分支，避免状态机落入再次执行 |
| HTTP 状态 | 协议错误与 call.status 分开 | 有效调用记录可用 200 返回失败/未知；不是 200 就等于发送成功 |
| 源码与模板 | 采用锁定版本核验过的 Cordis 机制，模板在 M0 编译 | 不混用不同版本教程的 Schema、ready/dispose 与事件 API |
| 通知与恢复 | 通知只唤醒，可靠样例持久保存位置/决定 | 允许临时监听；不把事件/动作分离说成任意重读都不会产生新动作 |
| QQ 接入 | 一个 onebot-v11 插件，具体服务实现可替换 | NapCat/SnowLuma 是候选实现，不是内核或插件类型 |
| 文档治理 | docs 是唯一正式文档，旧稿本地忽略归档 | 开发者使用同一套可追踪的接口与设计依据 |

## 2. 已采用的决策

| 编号 | 决策 | 代价/边界 |
| --- | --- | --- |
| D01 | 信息网关与自主应用；QQ 是首个闭环 | 平台与模型逻辑留在连接器/应用，不设前台角色 |
| D02 | Cordis 装配 + 独立内核 + 薄适配 | 同进程受信代码共享故障域，不是安全沙箱 |
| D03 | TypeScript/Node、SQLite、单 worker、Linux 单实例入口 | 实际依赖与锁行为在 M0 验证，不预建可替换底座 |
| D04 | JSON 事件信封与 source/id first-write-wins | 不验证重复正文等价，不保留原 JSON 字节 |
| D05 | bigint 序号、线上字符串、单 store_id | 不能自动识别未换标识的旧备份回滚 |
| D06 | 主动拉取 + 可丢失唤醒 | 无 ACK、租约或托管投递保证 |
| D07 | 显式能力、稳定 call_id 与结果查询 | unknown 停止自动重发，接受某些回复未自动完成 |
| D08 | 静态主体、来源和能力范围 | 接入方可见总体日志位置，多租户隔离后置 |
| D09 | 应用自主选择状态，参考 Agent 持久保存决定与进度 | 不强迫全部外部应用部署相同数据库 |
| D10 | 首版无事件/调用记录自动删除 | 持续占用增长，实际清理前补保留与去重期限契约 |
| D11 | M0—M2 + T01—T09，测试跟随真实功能 | 不把附件或灾难恢复变成首版前置 |
| D12 | 有限插件管理、可运行模板和演示 | 无市场、在线安装、无损热更新保证 |
| D13 | OneBot v11 标准优先、实现差异显式收敛 | 不承诺 v12 或全部实现功能兼容；切换实现须检查身份范围 |

D13 不要求为每个实现写一套插件，也不要求预先建设通用协议框架。标准路径优先，遇到实际差异再增加小的兼容适配。

## 3. 进入开发的条件

技术方向已足够明确。常规字段、状态、默认值和模块组织按本套文档实施；真正缺少的产品信息见[待决事项](open-questions.md)，按影响阶段解决。

依赖版本或协议行为出现新证据时，记录受影响契约、改变原因及必要测试。旧设计不会因保存在私有归档里重新成为实现要求。
