# 应用消费、参考 Agent 与恢复

统一开发基线 0.3 · 2026-10-18。本文规定参考应用的行为，不要求所有外部应用使用同一数据库或框架。网关读取规则见 [事件与存储](storage-and-recovery.md)，远端动作见 [能力契约](capabilities.md)。

## 1. 三种消费方式

| 方式 | 用途 | 应用承担的代价 |
| --- | --- | --- |
| 临时事件通知 | 控制台显示、短时指标 | 停用、断线或通知失败期间可能漏过，无恢复承诺 |
| 主动读取 + 本地位置 | 简单脚本、可重复计算任务 | 位置保存与业务操作之间可能存在重做或漏做窗口 |
| 读取 + 持久决策/结果 | 参考回复 Agent、需要恢复的变换应用 | 自己保存必要决定和位置，正确处理重启与远端 unknown |

插件和外部应用都可选择这些方式。通知不会代替持久接手；应用不需要注册 purpose、subscription 或 B1，也没有网关 ACK。

## 2. 输入范围和起点

一个参考读取器状态包含 input_id、store_id、source_prefix/type 等实际选择、last_seq。input_id 是应用内部稳定名称，不是网关消费者资源。

新实例先取得 info。面向实时回复的 Agent 默认把当时 latest_seq 作为起点，并原子保存这个明确边界；后续到达的消息从该边界继续读。历史上下文可以单独查询，不能被当作新的触发输入。演示变换和观察器可以显式从 0 开始。

恢复时使用保存的 store_id/last_seq，不因“又启动了一次”重新跳到 now。store_mismatch、position_ahead 或读取错误使输入暂停并报告，不自动跳过。

读取选择或服务端授权扩大后，旧位置只代表旧范围；操作者需决定新 input_id、显式重读或明确起点。不建设过滤版本协议，也不把这项选择隐藏在自动恢复里。

## 3. 参考 Agent 的最小持久状态

参考 Agent 使用自己的小 SQLite 状态库，单实例顺序做输入决策。它不是网关内置 Agent 引擎；用户已有后端可以按自己的方式实现相同责任。

| 状态 | 最少保存的内容 |
| --- | --- |
| input | input_id、store_id、选择范围、last_seq |
| decision | input_id、输入 source/id/seq、决定、选定文字、稳定 call_id（若回复）、执行状态、最近错误 |

对每个输入身份，每个 input_id 只有一份决定。某条消息在上下文中再次出现不产生第二份触发。回复调用使用独立稳定 call_id，不能每次网络重试生成新 ID。

决定可以是 no_reply、reply、ignored_stale。外发状态可以是 ready、in_progress、succeeded、failed、unknown；这些是本参考应用的本地词汇，不要求扩成公共工作流协议。

## 4. 决策与发送的顺序

1. 拉取一页，按序逐条处理，不在应用数据库事务中等待模型或网络。
2. 检查消息是否为允许的入站触发，选择上下文，调用模型。结果经本地校验后形成明确决定。
3. 将决定、已经选择的回复文字及 call_id 与这一条的进度共同提交。没有决定、无法保存或模型持续失败时，不越过该输入。
4. 发送循环从已保存的 ready 决定调用网关；重启也扫描这些未完成决定。不得把未保存的模型输出直接交给发送工具。
5. 网关返回已记录状态后更新本地执行状态；网络断开时查询同一 call_id，或用完全相同的参数重试调用。
6. unknown 保留为可见待核验记录，不自动换 ID 补发。它可以不阻塞后续消息决策，因为未决责任已经持久保存。

完成一页中所有匹配输入的上述接手后，可在事务中把 last_seq 推进到 next_after_seq，以越过无匹配记录。空页同样只在成功读取后推进。若中途退出，只提交已经接手的前缀；不要先保存整页末尾再逐条处理。

这一实现使用了先保存意图再执行的原则，但没有通用 inbox/outbox 服务、任务租约或分布式事务。它只保存回复样例实际需要的状态。

## 5. 中断后的预期

| 中断点 | 恢复行为 |
| --- | --- |
| 模型返回前或决定提交前 | 没有外发；从旧位置重读，可重新分析 |
| 决定提交后、首次调用前 | 使用已保存文字和 call_id，继续这一意图 |
| HTTP 响应丢失 | 查询原 call_id；不推导“没收到响应所以没发送” |
| 网关调用记录为 succeeded | 保存原结果，不再次执行 |
| 网关调用记录为 unknown | 显示待核验，停止自动补发 |
| Agent 或网关存储被回滚/更换 | 明确暂停，进入人工恢复流程，不声称跨回滚无重复 |

处理模式不等于平台端恰好一次。本方案偏向避免未知结果时的重复回复，因此接受某些调用可能最终没有自动发出。

## 6. 历史、积压与循环

参考 Agent 只对连接器映射为入站消息的事件做触发；自己发送的回流、派生分析和诊断事件可作为上下文，但默认不触发回复。不能仅靠 prompt 要求模型不要循环。

本地配置必须给出自动回复的最大事件年龄。测试配置采用 5 分钟；按事件可信来源时间判断，来源时间缺失时使用 accepted_at 并注明口径。超过窗口记录 ignored_stale 并推进；真实试用时可调整，不把它当全平台通用要求。

历史预览采用没有外部写权限的凭据或禁写模式。仅添加 replay 标签不能阻止发送。更改旧消息策略是产品选择，不自动清空 call_id 与决定记录。

## 7. 演示消费者

M0 已提供 fixture-transform 与 observer 的位置持久化和读取循环；observer 的本地事件副本属于 M2，参考 Agent 属于 M1。

- fixture-transform 只处理受控 fixture 事件，生成确定内容和稳定派生身份；发布成功后保存自己的位置。崩溃重试同一输出由网关 first-write-wins 处理。这个样例不承诺处理任意长 ID 或任意业务输入。
- observer 保存自己关心的信封与位置，可用一张本地事件表和一张位置表共同提交。它验证第二消费者独立暂停、继续和查询，不包含附件下载、全文检索或灾难恢复平台。
- 模拟工具返回输入摘要且无真实外部副作用。调用记录的故障测试另外使用受控的副作用测试提供者，输出到可丢弃测试目录。

参考读取循环每次只处理有界一页，不重入；忙时合并唤醒，空闲时按测试默认 1 秒补查，错误时有界退避。终止信号停止发起新读取，等待已进入持久提交的操作，再关闭本地状态库。

## 8. 能保证的范围

本方案能通过测试验证当前存储中的已接纳事件续读、参考应用的决定恢复和同一调用意图的本地去重。它不证明来源离线窗口已完整采集、不强迫其他应用达到相同标准，也不承诺用户删除/回滚状态后仍不重复。

对应 T03、T06、T07、T08；实际测试状态见 [验收](validation.md)。
